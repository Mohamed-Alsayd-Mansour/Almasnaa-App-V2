# المرحلة 1 — الخادم (Supabase) وترحيل بيانات 1.0

## الخطوات بالترتيب

### أ. تأكيد تجهيز Supabase
1. فعّل مزوّد Email، وأوقف التسجيل الذاتي وتأكيد البريد الإلكتروني كما هو موضح في دليل الإعداد.
2. طبّق ملفات SQL الأربعة بترتيبها مرة واحدة فقط: `0001_schema.sql` ثم `0002_guards_audit_rls.sql` ثم `0003_functions.sql` ثم `0004_accounts_admin.sql`. إذا أظهر استعلام التحقق أن جميع المكونات موجودة بالفعل، **لا تعِد تشغيل الملفات**.
3. قبل الترحيل، تحقق أن جداول البيانات فارغة؛ لا تنقل البيانات إلى قاعدة تحتوي على سجلات فعلية دون مراجعة.

### ب. إعداد بيئة الترحيل على جهازك
1. نزّل ملف تصدير الإصدار الأول `almasnaa-data-v1.json) وضعه في جذر مجلد المشروع. هذا ملف بيانات حقيقي، فلا ترفعه إلى GitHub ولا تشاركه.
2. انسخ `.env.example` إلى ملف جديد اسمه `.env` في جذر المشروع. السكربت المحدّث يقرأ هذا الملف تلقائيًا؛ متغيرات البيئة الموجودة في Windows لها الأولوية على القيم داخله.
3. املأ المتغيرات التالية في `.env` محليًا:
   - `SUPABASE_URL`: رابط مشروع Supabase.
   - `SUPABASE_SERVICE_ROLE_KEY`: مفتاح الخادم القديم `service_role) المطلوب لواجهة Admin API في السكربت الحالي. يبقى محليًا فقط ولا يدخل Flutter أو GitHub.
   - `SUPABASE_DB_URL`: سلسلة اتصال PostgreSQL المنسوخة من Connect في Supabase. استخدم Direct connection إن كان جهازك يدعم IPv6، وإلا استخدم **Session pooler** على المنفذ 5432. لا تستخدم Transaction pooler على المنفذ 6543 لهذا السكربت.
   - `SEED_PASSWORD_ADMIN`, `SEED_PASSWORD_MANSOUR`, `SEED_PASSWORD_QADRI`, `SEED_PASSWORD_SAYYAD`: كلمات المرور الأولية المعتمدة للحسابات الأربعة، بصيغة `@NNNN@` وبطول لا يقل عن 6 أحرف.
4. استخدم كلمة مرور قاعدة البيانات التي أنشأتها عند إعداد المشروع داخل سلسلة الاتصال. إذا احتوت رموزًا خاصة، اتبع تعليمات Supabase لترميزها داخل URI.
5. تأكد أن `.env` وملف البيانات والنسخ الاحتياطية وتقرير الترحيل ليست ضمن Git. أُضيفت هذه المسارات إلى `.gitignore`.

### ج. تشغيل الترحيل
من Terminal داخل جذر المشروع، نفّذ:
```powershell
python -m pip install psycopg2-binary requests
python scripts/migrate_v1.py --input almasnaa-data-v1.json
```

قبل تنفيذ أي إدخال، ينشئ السكربت نسخة من ملف v1 ويحسب SHA-256 في مجلد `backups/`. ثم ينشئ الحسابات الناقصة عبر Supabase Auth Admin API وينقل صفوف البيانات داخل معاملة SQL واحدة، ويتحقق من الأعداد ويكتب `migration-report.json`.

ملاحظة مهمة: إنشاء مستخدمي Auth يتم عبر API منفصلة عن معاملة PostgreSQL؛ لذلك لا يمكن ضمان تراجع إنشاء حساب Auth عند حدوث خطأ SQL لاحق. السكربت المحدّث يبحث عن حساب Auth ذي البريد الداخلي الثابت ويعيد استخدامه عند المحاولة التالية بدل إنشاء مستخدم مكرر. لا تغيّر كلمات مرور حساب موجود تلقائيًا.

### د. بعد الترحيل
1. لا تحذف ملف المصدر أو النسخة الاحتياطية.
2. افتح `migration-report.json` وتحقق من تطابق الأعداد: 64 غرفة، و132 اسمًا، و23 يومية، و186 إدخالًا.
3. راجع قائمة `needs_review` الخاصة بالإدخالات السبعة التي لا يوجد لها مالك واضح، وأسنِدها يدويًا من تبويب الأدمن في المرحلة الثانية حسب القرار المتفق عليه.
4. عيّن كلمة مرور النسخ الاحتياطي المستقلة من حساب الأدمن قبل استخدام عمليات التصدير أو الاستيراد أو حذف البيانات.

اليوميات الـ23 كلها مغلقة؛ نُسبت لمنصور/قدري حسب أغلبية الأسماء المكتوبة داخل إدخالاتها، ويومية الصياد تبقى لقدري (5 مقابل 1) ويراها الصياد أيضًا لأن إدخاله فيها.

## نتيجة الاختبار
`tests/run_local.sh almasnaa-data.json` على PostgreSQL 16 محلي (بديل بسيط لـ auth الخاص بـ Supabase): **79 اختبارًا ناجحًا**، تشمل الرؤية لكل دور، تقييد حقول الرصيص، اليوميات المتعددة والاستئناف دون تكرار، ثبات الملكية التاريخية، الإشعارات، كلمة مرور النسخ، التصدير/الاستيراد/الحذف الذرّي، الحساب المعطّل، وإعادة تشغيل الترحيل.
**لم يُختبر**: الاتصال الفعلي بمشروعك، و Admin API الخاص بإنشاء الحسابات (يعمل فقط في الوضع المحلي)، وRealtime.

## القرارات المعتمدة
1. كلمات المرور الأولية بصيغة `@NNNN@`، ثم تُغيّر كلمة مرور الأدمن عند أول دخول.
2. الإدخالات السبعة التي لا تملك مالكًا واضحًا تبقى للمراجعة ويُسنَد كل منها يدويًا من تبويب الأدمن.
3. صلاحية الرصيص في السجل محدودة بأربعة حقول في اليومية المغلقة؛ أما اليومية المفتوحة فتتبع سلوك الإصدار الأول.
4. اسم تصدير المشرف: `almasnaa-data-supervisor-{الاسم}.json`.
5. منفّذ العملية لا يتلقى إشعارًا بعمليته، بينما يتلقى الأدمن إشعارات عمليات المستخدمين الآخرين.

## مؤجل للمراحل التالية
خدمة إنشاء/تعطيل الحسابات وإلغاء الجلسات (Edge Function)، وضع «عرض كمستخدم» في التدقيق، المحادثات والمرفقات والتخزين، وكود Flutter كله. وملاحظة: بيانات 1.0 كانت في SharedPreferences (ملف JSON) وليست SQLite كما ورد في البرومبت.
